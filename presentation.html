CREDENTIAL SECURITY
Password Complexity: NIST & OWASP Standards
5 Mandatory Security Rules
  • Length (>= 8 characters): Protects against brute-force search space.
  • Uppercase Letter [A-Z]: Increases character space entropy.
  • Lowercase Letter [a-z]: Enforces diverse character sets.
  • Numeric Digit [0-9]: Defeats pure-dictionary word attacks.
  • Special Symbol [!@#$%^&*]: Prevents automated rainbow table matches.
Dual-Layer Architecture
  • Client-Side Live Evaluation: PasswordStrengthMeter.tsx evaluates keystrokes in real time, rendering checkmarks and a color-shifting bar (Red -> Amber -> Emerald).
  • Server-Side Authoritative Gatekeeper: validateStrongPassword() in server/utils/passwordValidator.ts re-validates the password before hashing.
  • Why Both? Client validation can be bypassed using cURL. The server-side check guarantees that weak passwords NEVER enter the database.
CRYPTOGRAPHY CORE
Password Hashing via Bcrypt (10 Salt Rounds)
Why Bcrypt Over MD5 / SHA-256?
  • The SHA-256 Flaw: SHA-256 is designed for fast file checksums (billions/sec on modern GPUs). Attackers can crack passwords in minutes using Rainbow Tables.
  • Adaptive Work Factor: Bcrypt uses 10 salt rounds ($2^{10} = 1024$ key expansion iterations). Intentionally consumes CPU cycles so brute-force guessing is economically impossible.
  • Unique Cryptographic Salt: Generates a random 22-character salt for each password. Identical passwords produce completely different stored hashes.
  • Timing Attack Defense: bcrypt.compare() executes in constant time, preventing microsecond analysis attacks.
Anatomy of a Stored Bcrypt Hash
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
├───┼──┼──────────────────────┼─────────────────────────────┤
 │   │            │                          │
 │   │            │                          └─ 31-char Hash Digest
 │   │            └─ 22-char Salt
 │   └─ Cost Factor (10 rounds = 1024 iterations)
 └─ Identifier ($2a$ = Bcrypt)

Crucial Viva Point: Hashing is strictly one-way! We never decrypt passwords. During login, we hash the candidate password with the stored salt and compare digests.

LOGIN WORKFLOW
User Authentication & Session Issuance Lifecycle
Login Lifecycle Steps
  • 1. Submit: User submits email and password on LoginPage.tsx.
  • 2. Normalize: Server trims and lowercases email address.
  • 3. Lookup: User.findOne({ email }). If not found, returns generic HTTP 401.
  • 4. Bcrypt Verification: bcrypt.compare(password, user.password) compares input against hash.
  • 5. Fetch Company: Loads organization data to enrich the session.
  • 6. Sign JWT: Generates 7-day session token and returns HTTP 200 with user profile.
Security Best Practices Applied
  • Anti-Enumeration Defense: Whether the email doesn't exist or the password was wrong, the error is always "Invalid email or password", preventing attackers from probing for registered accounts.
  • Hash Exclusion: Password hashes are excluded from JSON responses using select("-password").
  • Session Re-hydration: On browser refresh, AuthContext calls GET /api/auth/me using the stored JWT to verify the account is still valid.
SESSION TOKEN SPECIFICATION
JSON Web Tokens (JWT) & Stateless Architecture
Anatomy of an EcoTrack JWT
// Header.Payload.Signature
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJpZCI6IjY1ZjAxYT...",InJvbGUiOiJhZG1pbiIsImNvbXBhbnlJZCI6IjY1...
tj5n7wU8G3d9KpL...
  • Header: Algorithm (HS256) and token type (JWT).
  • Payload: Claims: id, role, companyId, exp (7 days).
  • Signature: HMACSHA256(Header + Payload, JWT_SECRET).
  • Tamper Proof: Modifying the role from "employee" to "admin" breaks the signature, triggering HTTP 401.
Stateless vs Stateful Sessions
  • Stateful (Traditional): Requires storing session IDs in RAM or Redis. Server must query database on EVERY request. Hard to scale.
  • Stateless (EcoTrack JWT): Session data is contained inside the signed token itself.
  • Zero DB Lookups: Verified in-memory in microseconds using JWT_SECRET.
  • Horizontal Scale: Any backend server instance can verify incoming tokens instantly.
FRONTEND NETWORKING
Client-Side Token Interception (Axios Interceptor)
Implementation in src/api/axiosClient.ts
apiClient.interceptors.request.use((config) => {
  const storedAuth = localStorage.getItem("auth");
  if (storedAuth) {
    try {
      const { token } = JSON.parse(storedAuth);
      if (token) {
        config.headers.Authorization = `Bearer ${token}`;
      }
    } catch {}
  }
  return config;
});
Why This Architecture Matters
  • Zero Boilerplate: Eliminates manual Authorization headers across 50+ component API calls.
  • Separation of Concerns: UI components focus on data and charts; network security is centralized.
  • RFC 6750 Standard: Follows standard OAuth 2.0 Bearer token authorization format.
  • Automatic Session Re-hydration: Works seamlessly with browser page reloads.

PASSWORD RECOVERY
Account Recovery: 3-Step State Machine Workflow
Step 1: Email Request
  • User submits registered email.
  • Server checks user existence.
  • Generates 6-digit numeric OTP.
  • Hashes OTP with Bcrypt before saving.
  • Stores in MongoDB with 10-min TTL.
  • Sends HTML email via Nodemailer.
Step 2: OTP Verification
  • User enters 6 digits in auto-focus boxes.
  • Rate-limited to max 5 failed attempts.
  • Compares input with stored Bcrypt hash.
  • Deletes OTP immediately on match.
  • Issues 15-min single-purpose reset JWT.
  • 60-second cooldown timer for resend.
Step 3: Password Reset
  • User enters new password with live meter.
  • Verifies 15-min reset JWT signature.
  • Validates NIST/OWASP complexity rules.
  • Hashes new password with Bcrypt (10 rounds).
  • Updates password in database.
  • Redirects to Login with success toast.
TEMPORARY CREDENTIAL MANAGEMENT
OTP Cryptography & MongoDB TTL Indexes
OTP Cryptography & Hashed Storage
  • Cryptographic Randomness: Generated using crypto.randomInt(100000, 1000000). Unlike Math.random(), this uses OS entropy and is unguessable.
  • Why Hash OTPs in MongoDB? We never store plain OTPs! If the database were leaked, an attacker could read valid OTPs and reset passwords within the 10-minute window. Bcrypt hashing protects the OTP even during a database breach.
  • Attempt Counter: Increments on every wrong guess to detect brute-force attacks.
MongoDB TTL (Time-To-Live) Index
// server/models/Otp.ts
createdAt: { 
  type: Date, 
  default: Date.now, 
  expires: 600 // 10 minutes
}
  • Automatic Self-Destruction: MongoDB's background thread monitors indexed Date fields and automatically purges expired documents.
  • Zero Maintenance: No cron jobs, no background task scripts, zero database bloat.
ACCOUNT RECOVERY SECURITY
Brute-Force Defense & 15-Minute Reset Tokens
Brute-Force Attack Mitigation
  • The Mathematical Attack Surface: A 6-digit numeric OTP has $10^6$ ($1,000,000$) combinations. An automated script could brute-force this in minutes without limits.
  • Our Defense:
    1. Short 10-minute lifetime via TTL index.
    2. Maximum 5 failed attempts limit stored in MongoDB.
    3. If attempts >= 5, the OTP document is permanently deleted and returns HTTP 429.
  • Statistical Result: An attacker gets only 5 guesses out of 1,000,000 ($0.0005\%$ chance), making brute-force attacks statistically impossible.
Single-Purpose Reset Tokens
  • Why Not Reset in Step 2? Once OTP matches, the user moves to Step 3 to type a new password. The OTP is deleted immediately so it cannot be replayed.
  • The Reset Token: Server issues a signed JWT: { id, email, purpose: 'password_reset' } valid for 15 minutes only.
  • Endpoint Guard: POST /api/auth/reset-password strictly checks decoded.purpose === 'password_reset'. Standard session tokens are rejected.

AUTHORIZATION ARCHITECTURE
Dual-Layer Role-Based Access Control (RBAC)
Layer 1: Frontend Route Guard (ProtectedRoute)
  • Implementation: <ProtectedRoute allowedRoles={['admin']}> in src/App.tsx.
  • Client-Side Behavior:
    1. Waits for session re-hydration (isLoading === false).
    2. If unauthenticated -> redirects to /login.
    3. If user's role is not in allowedRoles -> redirects to /dashboard.
  • Purpose (User Experience): Hides unauthorized UI links and prevents navigation crashes.
Layer 2: Server Middleware Guard (requireRole)
  • Implementation: router.delete('/departments/:id', requireAuth, requireRole(['admin']), handler).
  • Server-Side Behavior: Reads req.user.role from verified JWT. If unauthorized, terminates request immediately with HTTP 403 Forbidden.
  • Why Server RBAC is Mandatory: Client-side code can be modified in browser dev tools. The Express middleware is the authoritative security boundary that protects database operations.
ENTERPRISE DATA PRIVACY
Multi-Tenancy Security & Data Isolation
Database Multi-Tenancy
  • Shared Cluster, Isolated Data: All organizations share the same MongoDB database, minimizing cloud operational costs.
  • Foreign Key Scoping: Every User, Department, and CarbonLog document includes a mandatory companyId.
  • Query-Level Scoping:
    CarbonLog.find({ companyId: req.user.companyId })
  • Zero Cross-Tenant Leakage: Even if a user guesses another company's log ID, queries return null because the companyId does not match.
Defense-in-Depth Principles
  • Password Hash Sanitization: User.findById().select('-password') ensures password hashes are never returned in JSON responses.
  • Startup Health Checks: getJwtSecret() crashes immediately on server boot if JWT_SECRET is missing, preventing insecure default secrets.
  • CSRF Resilience: Stateless Bearer tokens are immune to Cross-Site Request Forgery because browsers do not automatically attach custom Authorization headers.

EXAMINATION PREPARATION
Key Viva Questions & Technical Code Defense
Top Architectural Viva Questions
  • Q: Why Bcrypt instead of SHA-256?
    A: SHA-256 is designed for fast hashing and is vulnerable to GPU brute force and Rainbow Tables. Bcrypt has an adaptive cost factor (10 rounds = 1024 iterations) and unique random salts.
  • Q: What if an attacker alters their role in a JWT?
    A: Tampering invalidates the HMAC-SHA256 signature calculated with JWT_SECRET. The server rejects it immediately with HTTP 401 Unauthorized.
  • Q: Why not store plain OTPs in MongoDB?
    A: If the DB is leaked, attackers could read active OTPs and hijack accounts. Hashing with Bcrypt ensures OTP confidentiality even during a database breach.
Top Implementation Viva Questions
  • Q: Difference between ProtectedRoute and requireRole?
    A: ProtectedRoute is a frontend React guard for user redirection; requireRole is the authoritative backend Express middleware that returns HTTP 403 Forbidden.
  • Q: What is MongoDB TTL and why use it?
    A: Time-To-Live index that automatically purges OTP documents 10 minutes after creation, eliminating database bloat without cron jobs.
  • Q: How does the Axios Interceptor work?
    A: It intercepts outgoing HTTP requests, reads the JWT from localStorage, and stamps 'Authorization: Bearer <token>' automatically.
